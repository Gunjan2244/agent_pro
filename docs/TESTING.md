# Testing and verification

## Mobile app (Kotlin Multiplatform)
- Run `cd mobile && ./gradlew :build-logic:test verifyShared :androidApp:assembleDebug :androidApp:lint :composeApp:testAndroidHostTest`.
  - Run one Gradle invocation at a time on the dev machine (memory), and `./gradlew --stop` afterwards.
  - `verifyShared` is part of `check`.
  - `:composeApp:testAndroidHostTest` runs `commonTest` (and `androidHostTest`) on the JVM. With AGP's KMP library plugin it replaces `testDebugUnitTest`, which doesn't exist for `composeApp`.
  - `:build-logic:test` runs the codegen and verifier unit tests (also `./gradlew -p build-logic test`).
  - After changing `shared/`, run `./gradlew generateShared` first. It writes the `catalog_sync` migration, `shared/generated/privacy-notices.json` and updates the keys lockfile; otherwise `verifyShared` fails and says why.
  - **Before any release** (app or web), run `./gradlew verifyReleaseReady`: it fails while fill-in placeholders such as `{GRIEVANCE_EMAIL}` remain in `shared/i18n` (Android release builds run it automatically).
  - In the iOS phase, on a Mac, add `:composeApp:iosSimulatorArm64Test`.

## Database
### Locally (no Supabase project needed)
Run `bash supabase/tests/run.sh` from anywhere in the repo (it is a bash script; `sh` fails). It needs Docker, and the generated `*_catalog_sync.sql` must exist (run `./gradlew generateShared` in `mobile/` first; `run.sh` stops with that message otherwise).
- **What it does:**
  1. Starts a throwaway `postgres:15` container (`agentpro-sqltest`, `--memory=384m`). Override the image with `PG_IMAGE=postgres:17` and the container name with `CONTAINER_NAME=…` (use your own name when other runs may be going on in parallel).
  2. Applies `supabase/tests/00_supabase_shim.sql`, which is a stand-in for Supabase's roles, `auth`, `storage` and the realtime publication, **for local tests only**.
  3. Applies `supabase/migrations/*.sql` in order.
  4. The generated `*_catalog_sync.sql` is part of step 3 (it sorts last). The old Python fixture is retired, so the tests always run against the real generated SQL.
  5. Copies the latest `catalog_sync` and the demo seed `supabase/demo/demo_offers.sql` into the container and runs `supabase/tests/[1-9]*.sql` in one session, with the psql variables `catalog_sync` and `demo_offers` set to their paths, so a test can re-apply the catalog with `\i :catalog_sync` or run the demo seed with `\i :demo_offers` (inside a transaction that rolls back).
- **Output:** one `PASS | …` or `FAIL | …` line per check, then any unexpected SQL errors and a summary. It exits non-zero on any failure or error.
- **Cleanup:** the container is removed afterwards. Set `KEEP=1` to keep it for debugging.
