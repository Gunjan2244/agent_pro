# Web renderer — public agent sites

There's one static site for **every** agent. Content is fetched at runtime, so agents never need a redeploy when they edit or publish.

## Hosting
- **Current deployment (2026-10-17):** a preview at `https://agentpro-sites.sledjesoftwares.workers.dev` (demo data only), built with `SITE_BASE_URL` set to that URL. `_headers` uses `! Cache-Control` so `/config.js` (`no-store`) and `/a/*` (`no-cache`) get exactly one value.
- **Cloudflare Workers static assets** (DECISIONS #59): a Worker named `agentpro-sites`, config in `web/wrangler.jsonc`, assets served from `web/dist`. The Worker script (`web/worker.js`, with `ssr.js`, `headers.js`, `portal.js`, `portal-sw.js`, `cookies.js`, `templates/index.js` and the pure code they import; bundled by wrangler, not copied into `dist`) runs **only** for `assets.run_worker_first = ["/", "/a/*", "/my", "/my/*", "/join", "/join/*", "/privacy", "/manifest.webmanifest", "/robots.txt", "/sitemap.xml"]` (DECISIONS #65, #75). Every other request (fonts, CSS, JS, JSON, `/terms`) is served straight from the assets without invoking it. Agents' own domains attach as Cloudflare for SaaS custom hostnames (DOMAINS.md) and use the same paths. The platform domain is not bought yet, so there are no routes or custom domains in the config; the preview lives at `agentpro-sites.<account-subdomain>.workers.dev` (`workers_dev = true`).
- **Routes (Worker):**
  | request | response |
  |---|---|
  | `GET\|HEAD /a/<slug>` | **301** to `/a/<slug>/`, query kept, no backend call |
  | `GET\|HEAD /a/<slug>/`, `/a/<slug>/privacy`; custom host `/`, `/privacy` | **200** server-rendered HTML (`Cache-Control: no-cache`, `Last-Modified`, or **304** on `If-Modified-Since`) |
  | same, but unknown, unpublished or lapsed site, or a malformed slug | **404** SSR "This page isn't available", `noindex`, no agent data, no scripts |
  | same, but the backend (or `config.js`, or rendering) fails | the static shell `index.html` (200), so the browser renders and retries |
  | `?preview=1` or any `?mock` | the shell, never SSR'd, no backend call |
  | `?install=1` | SSR'd, with `<meta name="robots" content="noindex">` (canonical stays the clean URL) |
  | `/` or `/privacy` or `/terms` on the primary host with no slug (platform pages); a custom host's other paths (`/a/*`) | the assets (shell) as before |
  | `GET\|HEAD /a/<slug>/my[/login\|/start]`; custom host `/my[/…]` | the customer portal's pages, **200** server-rendered, `Cache-Control: no-store`, `X-Robots-Tag: noindex, nofollow`; `/my` without a session **303**s to `/my/login`. See [Customer login (portal)](#customer-login-portal-decisions-98100) |
  | `POST /a/<slug>/my/{login,start,ask,request,logout}` | form posts, answered by **303** (PRG) or the same page with an inline error (400/429); `415` non-form content type, `403` foreign `Origin`, `413` over 4 KB, `405` other methods |
  | `GET /a/<slug>/my/sw.js` | the portal's service worker (below); 404 while the portal is off |
  | any other path under `/a/<slug>/my/…` | **404** portal "unavailable" page (`no-store`, `noindex`) |
  | `GET /manifest.webmanifest` | the agent's manifest (below); `&app=portal` gives the portal's manifest |
  | `GET /robots.txt` | allow `/`; disallow `/*?preview`, `/*?install`, `/*?mock` (and the `&` forms), `/a/*/my`, `/my`, `/a/*/join`, `/join`; `Sitemap: <request origin>/sitemap.xml` |
  | `GET /sitemap.xml` | see "Crawling" |
  | other methods | 405 on manifest/robots/sitemap; page routes pass to the assets |
- **Static data (per isolate):** the Worker reads `config.js`, `site-schema.json`, `catalog.json`, the templates registry, `design-tokens.json`, the privacy notices and each locale's dictionary through `env.ASSETS`, and caches them per isolate (keyed by the binding; a failed load is not cached). Changes to those files only arrive with a deploy, which restarts isolates.
- **Build:**
  - `sh scripts/build-web.sh` copies `web/` and `shared/` into `web/dist/`.
  - It writes `web/dist/config.js` from the `SUPABASE_URL` and `SUPABASE_ANON_KEY` environment variables, plus `BUILD_TIME` (the build's UTC time, ISO), which the Worker uses for `Last-Modified`.
  - It copies `web/images/` (the bundled illustrations and their `manifest.json`, docs/IMAGES.md).
  - It generates `tokens.css` from `design-tokens.json`.
  - It generates `icons/<swatch>-192.png` and `-512.png` for every `catalog.accentSwatches` entry (`scripts/gen-icons.mjs`, the web app manifest icons).
- **SPA routing:** `assets.not_found_handling = "single-page-application"` serves `/index.html` for any path that is not a real file. The Worker relies on it for the shell (`/a/<slug>/`, `/terms`). Because `run_worker_first` is an array, the routing is explicit: only the paths above reach the Worker.
- **Headers:** `web/_headers` (copied into `dist/`, not served as an asset) sets the same security headers for static assets; **the Worker's HTML responses carry them from `web/headers.js`** (`_headers` does not apply to Worker responses; `test-web.mjs` asserts the two are equal). It sets `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, a minimal `Permissions-Policy` and a CSP (`self` + `*.supabase.co` for `connect-src`/`img-src` ; `style-src 'self' 'unsafe-inline'`, `font-src 'self'`: no third-party font origins, the fonts are self-hosted). Filenames are not hashed, so assets get `max-age=300, stale-while-revalidate=86400`; `/index.html` is `no-cache` and `/config.js` is `no-store`. Worker HTML is `no-cache` (no edge cache in v1, DECISIONS #75). `_headers` allows 100 rules and applies only to static-asset responses.
- **Automatic deploy (DECISIONS #118, 2026-10-28):** `.github/workflows/deploy-web.yml` runs on every push to `main` that touches `web/**`, `shared/**` or the build/test scripts. It runs `node scripts/test-web.mjs` and `node scripts/lint-web-css.mjs`, builds with `sh scripts/build-web.sh` (no `RELEASE=1` — see below), then `npx wrangler@4.151.1 deploy --config web/wrangler.jsonc`, authenticated with the `CLOUDFLARE_API_TOKEN` / `CLOUDFLARE_ACCOUNT_ID` repo secrets (no `wrangler login`). `SUPABASE_URL` and `SUPABASE_ANON_KEY` also come from repo secrets; `SITE_BASE_URL` from the `SITE_BASE_URL` repo variable, defaulting to the preview URL above. This is the one exception to CLAUDE.md's per-deploy approval rule (the user chose it explicitly); a failing test or lint step blocks the deploy. A manual deploy is still possible and unchanged: `sh scripts/build-web.sh` (real env, never `WEB_DEV=1`), then `npx wrangler@4.151.1 login` once, then `npx wrangler@4.151.1 deploy --config web/wrangler.jsonc`. Check config without deploying: `npx wrangler@4.151.1 deploy --dry-run --config web/wrangler.jsonc`.
- Public launch waits for the P1 privacy items (PRIVACY.md); until then both the automatic and manual builds stay on the preview path (`RELEASE` unset, demo data only). `scripts/release-check.mjs` reports the unfilled placeholders; once it's empty, the workflow's build step should switch to `RELEASE=1 sh scripts/build-web.sh`.
- Build env: `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SITE_BASE_URL` (the primary host, default `http://localhost:8080`). `web/dist/` and `web/config.js` are git-ignored.
- **Every other deploy path (manual, or any future Worker) still needs the user's approval each time.** Record each deploy in STATUS.md (Environment) and in CHANGELOG.md — the pipeline's deploys too.

The sections are rendered from the data in `site-schema.json` (default CTA via `defaultKey`, option labels for languages and highlight icons, the pinned sections). Interests come from `catalog.json`; the accent hex comes from `catalog.accentSwatches`; supported locales from `catalog.locales`; valid template keys from `shared/templates/index.json`. `app.js` loads site-schema, catalog and the templates registry at runtime; nothing in `web/` hard-codes them (the accent fallback is `var(--c-primary)`). `tokens` passed to `render` is `{ accent, schema, catalog, notice, privacyHref, family, images, seed, today? }` (`catalog.insuranceTypes` labels the companies' types): `family` is the template's registry family (`personal` | `offers`, `familyOf`), `images` the parsed `web/images/manifest.json` (`{}` when absent), `seed` the slug or custom host (it picks the hero scene), `today` an optional `YYYY-MM-DD` for tests (default: today in Asia/Kolkata). `ssr.js` and `client.js` fill them the same way, so the SSR body still equals `render()`.

## Resolution
0. A `?preview=1` page does no resolution at all, on the server or the client; it waits for `window.renderSite(json)` (the in-app preview). The app loads it live as `/?preview=1` (DECISIONS #119), so every deploy changes what agents see in the app too: `renderSite` must keep accepting the payloads that older app versions send. The preview never submits enquiries or records views.
1. If the host is the primary host (`SITE_BASE_URL`), read the slug from `/a/{slug}`, falling back to `?s={slug}`. Then call `get_public_site`.
2. Any other host is a custom domain: call `get_public_site_by_host(location.hostname)` and render at `/`. Only `active` and `renew_soon` domains resolve; an expired domain shows "This page isn't available", while the free link keeps working.
3. If the site isn't found, isn't published, or **its owner's plan has lapsed** (BILLING.md), show a friendly "This page isn't available" message with no agent data. The Worker does steps 1 to 3 on the server (same `resolveTarget`, same `get_public_site*` RPCs through its own `rpc()`); the client repeats them only in the fallback render.

## Templates
Templates are **pure functions**:
```js
export function render(site, t, tokens) { return htmlString }
// site = { content, template_key, accent, locale, profile }, t = i18n lookup
```
- A template only arranges the shared section partials and supplies its CSS layout.
  - Section order and visibility come from `content.sectionOrder` and `content.hidden`.
  - Fields come from `site-schema.json`.
- Because they're pure, the same code runs in three places:
  1. the browser,
  2. the in-app preview (`SitePreview`: an Android WebView now, WKWebView on iOS later), which loads this Worker's `/?preview=1` shell (falling back to the web files bundled in the app when it can't be reached, DECISIONS #119) and calls `window.renderSite(json)` with the unsaved draft (plus, when the signed-in RPC `preview_site_offers` answered, top-level `offers` and `company` in the `get_public_site` shapes, DECISIONS #84; without them the page renders as before), and
  3. the Cloudflare Worker, which server-renders every public page (next section).
- **Colours** always come from `tokens.css` plus `--accent`, set from the agent's swatch.
- **Look:** clean and professional, matching the app (DESIGN_SYSTEM.md "Website theme"). Redesigned 2026-10-22 (PRODUCT.md requirement log) so every page uses one planned system; before/after screenshots went to the user, nothing is deployed.
  - White background, the Inter font and generous whitespace.
  - One call to action per section.
  - The accent is only for buttons, links and small highlights, never for large colour blocks.
  - **Layout system (`styles/base.css`, shared by all five):**
    - **One grid:** every section, the hero and the footer share one content width, `--wrap` (1080 px; minimal 640 px), and one gutter, `--gutter` (16 px, 24 px from 720 px). Reading text (prose, the lead, the FAQ, lists, disclaimers) is held to `--measure` (720 px).
    - **One rhythm:** each section has `--sec-y` above and below it (24 px on phones, 48 px from 1024 px), so sections are 48 / 96 px apart. They're separated by **whitespace only**: no hairline between sections (the design system allows hairlines only between list rows). The hero gets 48 px (72 px from 1024 px) above it.
    - **Headings:** `<h1>` 39 px, 65 px from 1024 px (minimal 23 px); every section `<h2>` 23 px 600 with 24 px below it. Each template styles all of its `<h2>`s the same way (classic: centred with a short accent rule under it; modern: a 48 px accent rule above it; minimal: a small uppercase muted label; the Best offers family: plain).
    - **Components:** one card (white, hairline, 12 px corners, 16 px / 24 px padding from 720 px); buttons 48 px tall with 12 px corners; quick-interest **chips** (40 px outlined pills, links) and static **tags** (32 px grey pills: insurance types, the compact interest list); grids of 1 / 2 / 3 columns (720 / 1024 px) for services, companies, offers and testimonials, 2 / 4 for highlights; offer cards are flex columns whose footer (ends date, CTA, fine print) sits at the bottom, so cards in a row line up; the **FAQ is a normal accordion** (`<details>` rows with hairlines, the question 600 with a "+"/"−" on the right, 48 px tall); the enquiry form is a card with full-width inputs and button, and the consent checkbox is 20 px, aligned with the first line of its text; the **footer** is a pale `surfaceContainerLow` band aligned to the grid; the sticky Call / WhatsApp bar is unchanged.

## Server-side rendering and hydration (DECISIONS #75)
- **Flow:** request → `worker.js` resolves the target → `get_public_site*` → `ssr.js renderDocument()` → HTML. Nothing in the first response needs JS.
- **The document** contains, in order: `<html lang>`; `<title>`, `description`, `robots`, `canonical`, `og:*`, `twitter:*` from `headData()`; the manifest, icon, apple-touch-icon and `apple-mobile-web-app-title` links (what the fallback `installable()` adds in the browser); the Inter latin-400 font preload; `fonts.css`, `tokens.css`, `base.css` and the template's `style.css`; the JSON-LD; then `<main id="root" data-ssr>` holding **exactly** the template's `render()` output (a test asserts this for every template and locale), `<script type="application/json" id="boot">` (slug, host, locale, template key, `page` = `privacy` or null, plus the agent's `name` and `phone`, which the thank-you message needs; `<` and the line separators are escaped so agent text cannot close the script), `config.js` and `app.js` (a deferred module).
- **Privacy page:** `privacyHtml()` is pure, so `/a/<slug>/privacy` and a custom host's `/privacy` are server-rendered too (indexable, canonical = itself, no template CSS). The request form is wired by `hydrate.js` (`wirePrivacy`).
- **Hydration (`hydrate.js`):** reads `#boot`; loads the dictionary, catalog and notices; `wireForm` (consent, interest, submit); a delegated click handler for `a[data-interest]` chips that preselects the form's interest when the option exists; `wireInstall` (the button and `?install=1` sheet; no head links, the HTML already has them); one `record_site_view` per session (not with `?install=1`). It never writes markup (a test checks the source and runs it against a fake DOM). A normal page therefore loads only `app.js` + `hydrate.js` + `api.js`, `i18n.js`, `form.js`, `sections/util.js` (+ `install.js`); `client.js`, the sections and the templates are never downloaded.
- **Client render (`client.js`)** is kept for the in-app preview (`renderSite`), `?mock=1`, and the fallback when the Worker could not render. `app.js` defines `window.renderSite` immediately and loads `client.js` on the first call, so the app can call it as soon as the page has loaded.
- **Conditional requests:** `Last-Modified` is **max(`site.published_at`, `BUILD_TIME`)** (`lastModified(site, cfg)` in `worker.js`; `BUILD_TIME` comes from `config.js` through `parseConfig`), so a deploy that changes a template or its CSS also invalidates browsers' copies, not only a re-publish. A matching `If-Modified-Since` gets a 304 before any rendering. Without `published_at` there is no `Last-Modified`.
- **One URL form:** `/a/<slug>/`. The Worker 301s the slashless form; the canonical URL, the manifest `scope`/`start_url`, the back link from the privacy page and the client fallback all use it. (There is no client `history.replaceState` any more.) `/a/<slug>/privacy` has no trailing slash.

## Crawling
- **`robots.txt`:** see the route table. It is the same on every host and names the requested origin's sitemap.
- **`sitemap.xml`:**
  - *custom domain:* `https://<host>/` and `https://<host>/privacy`, `lastmod` = `published_at` when known (`get_public_site_by_host`; an unknown domain gets a 404).

  - **iOS:** Safari reads the manifest (16.4+) and the apple-touch-icon; there's no prompt API, so the button and sheet show the Share-sheet steps.

## Customer login (portal) (DECISIONS #96–#100)
An agent's customers sign in at **`/a/<slug>/my`** (`/my` on a custom domain) and see their policies, dues and recorded payments. Everything is server-rendered by the Worker (`handlePortal` in `worker.js`; pure pages in `portal.js`); the page JS never sees the session. The RPCs and rules are in BACKEND.md, "Customer portal". Nothing here is deployed yet.
- **Routes** (`route.js`: `resolveTarget` returns `page: "portal"` and `portalPath` = `""` | `login` | `start` | `ask` | `request` | `logout` | `sw.js`, or `null` for any other path, a 404; `portalLinks(target)` gives `base`, `home`, `login`, `start`, `ask`, `request`, `logout`, `sw`, `site`, `privacy`):
  | request | behaviour |
  |---|---|
  | `GET /my` | the home page with a session; otherwise **303** to `/my/login` |
  | `GET /my/login` | the sign-in form (mobile + PIN); `?done=signed_out` shows "You've signed out" |
  | `GET /my/start?t=<token>` | a well-formed token is moved out of the URL: **303** to the bare `/my/start` with `ap_invite=<token>; Path=<base>/start; Max-Age=900; HttpOnly; Secure; SameSite=Lax` (DECISIONS #101). A malformed token shows the "link isn't valid" error, no backend call |
  | `GET /my/start` | the first-login form when the `ap_invite` cookie is present; otherwise the "link isn't valid" error. `Referrer-Policy: strict-origin` on every start response. **Never `no-referrer` or `same-origin`**: Chromium then sends `Origin: null` on the same-origin form POST and the Origin check rejects the first login |
  | `POST /my/login` | `portal_login`; on success **303** home with the cookie. Errors re-render the form (400): wrong mobile or PIN (one generic message), `locked` ("try again in {minutes}") or hard-locked ("ask {name} for a new link") |
  | `POST /my/start` | takes the invite token from the `ap_invite` cookie (no hidden `t` field; no cookie → "link isn't valid", no RPC), checks the PIN twice and the consent box, then `portal_activate` with the `customer_portal` notice's `{notice_key, version, hash}` (hash for the page's locale) and the typed mobile; success → **303** home with the session cookie and `ap_invite` cleared; `invalid_invite` also clears it; `rate_limited` → 429 |
  | `POST /my/ask`, `/my/request` | `portal_ask` / `portal_request`; success → **303** to `/my?done=asked` or `?done=requested` (a one-line confirmation); `session` → login and the cookie cleared |
  | `POST /my/logout` | `portal_logout` (`everywhere=1` for "Sign out on all devices"); then **303** to `/my/login?done=signed_out`, the session cookie cleared **even if the RPC fails**. No `Clear-Site-Data` (on the shared origin it would clear every agent's site cache, and it does not clear service-worker caches); the signed-out login page tells the service worker to wipe instead (below) |
  | `GET` on `/my/ask`, `/my/request`, `/my/logout` | **303** home (a stray link) |
  | `GET /my/sw.js`, `GET /manifest.webmanifest?…&app=portal` | below |
  | unknown, unpublished or lapsed site; portal off (flag, `showCustomerLogin: false`); unknown portal path | **404** portal "unavailable" page: `no-store`, `noindex`, no agent data, no scripts |
  | the backend or `config.js` fails | **503** portal error page (`portalErrorDocument`, no agent data). **Never the static shell**, so a customer's page never falls back to the client render |
  | other methods | 405 |
- **Session cookie** (`cookies.js`): `ap_portal=<token>; Path=/a/<slug>/my` (`/my` on a custom domain); `Max-Age` = the RPC's `expires_at` (90 days); `HttpOnly; Secure; SameSite=Lax` (Lax so a link from WhatsApp arrives signed in). Only the Worker reads it (a malformed value is treated as none); the RPCs get the bearer token in the call. Because the path is per site, one browser can hold a separate login for each agent.
- **Secret header** (DECISIONS #101): the six portal RPCs (`portal_activate`, `portal_login`, `portal_home`, `portal_ask`, `portal_request`, `portal_logout`) are called with `x-portal-key: <env.PORTAL_RPC_KEY>`; the site RPCs are not. The key is a Worker secret (`npx wrangler@4.151.1 secret put PORTAL_RPC_KEY`), never a var or in `config.js`. Without it the portal fails closed: **503** portal error page and no RPC, logged once without the value. `{ok:false,error:'rate_limited'}` from login or start renders the "too many attempts" message with 429.
- **CSRF:** SameSite=Lax plus, on every POST, `Content-Type: application/x-www-form-urlencoded` (else 415) and an `Origin` header equal to the request's origin (else 403). Bodies over 4096 bytes are refused with 413 before the RPC.
- **Headers:** the normal `SECURITY_HEADERS` (CSP `script-src 'self'`, `frame-ancestors`/`X-Frame-Options: DENY`, …) plus `Cache-Control: no-store` and `X-Robots-Tag: noindex, nofollow` on every portal response. `robots.txt` adds `Disallow: /a/*/my` and `Disallow: /my`. Portal pages are not in the sitemap. The pages work without JS.
- **Rate limit:** the `PORTAL_LIMIT` Workers rate-limit binding (10 requests per 60 s per `cf-connecting-ip`, declared in `wrangler.jsonc` `ratelimits`) is checked on every POST that needs it; over the limit → **429** with the page's "too many attempts" message, no RPC call. The Worker skips the check when the binding is absent (local runs and tests). It protects the bcrypt cost of `portal_login`/`portal_activate`.
  > TODO(doc): the `ratelimits` block in `wrangler.jsonc` (and `namespace_id: "1001"`) was written without a `wrangler deploy --dry-run`; verify it against the wrangler schema before the first deploy.
- **Pages** (`portal.js`; every string is `portal.*` or `site.*` in `shared/i18n`, escaped; the agent's accent and photo or monogram in the header; EN and HI):
  - **Sign in:** mobile + 6-digit PIN (`type="password" inputmode="numeric"`), and "No PIN yet? Ask {name}" with a WhatsApp link when the agent has a number.

## Customer sign-up page (DECISIONS #108)
The agent shares a link; the customer agrees to a privacy notice, fills in a form that is **autosaved as they type** (so the agent watches it live in the app's Incomplete forms) and presses **Submit**, which adds them as a customer. Server-rendered like the portal and working without JS; the contract of the RPCs is in BACKEND.md. Files: `join.js` (pure renderer, `joinLinks`, `JOIN_FIELDS`), `join-age.js` (`isMinor`, `todayIST`, shared with the browser), `join-client.js` (the only script), `styles/join.css` (on top of `portal.css`), `handleJoin` in `worker.js`, `joinToken`/`joinCookie` in `cookies.js`, and the `join` targets in `route.js`.
- **Routes:** `/a/<slug>/join[/consent|save|submit|done]` on the primary host and `/join[/...]` on a custom domain (`resolveTarget` gives `{page:"join", joinPath}`; `null` for any other subpath = the 404 page). `wrangler.jsonc` `run_worker_first` has `/join` and `/join/*`. Every response is `no-store` with `x-robots-tag: noindex, nofollow`, the `SECURITY_HEADERS` (CSP: no inline script) and `Referrer-Policy: strict-origin` (for the same reason as the portal's start page); `robots.txt` disallows `/a/*/join` and `/join`.
- **Token:** `GET <base>/join?t=<token>` moves a well-formed token into the `ap_join` cookie (`Path=<base>/join`, `Max-Age=604800`, `HttpOnly; Secure; SameSite=Lax`) and answers **303** to the bare `<base>/join`; the token never stays in the URL and the page JS never sees it. A malformed `t` or no cookie shows the invalid-link page.
- **Gate:** every anon RPC (`signup_open|consent|save|submit`) is sent with `x-portal-key` from `env.PORTAL_RPC_KEY` (the portal's secret, DECISIONS #101); without it every route answers **503** and makes no RPC (the save route answers 503 JSON). A backend or asset failure is a 503 error page, never the SPA shell.
- **Pages:** `GET join` calls `signup_open`. *Not consented:* the notice (`privacy.customer_signup.title/what/why/who/how_long/rights` with `{name},{phone},{email}`), a link to the site privacy page's `#signup` section, an unticked required checkbox (`privacy.customer_signup.consent`) and **Start** (`POST consent`, a normal form post); **no form field is rendered before consent**. *Consented:* the form (name*, mobile*, email, date of birth, address, city, nominee) prefilled with the saved values, the save-status line and **Submit** (`POST submit`). `invalid_link` (unknown, used, expired, deleted) clears the cookie and shows "This link has expired or was already used. Ask {name} for a new one." with Call and WhatsApp; `unavailable` is the 404 "not available" page. `GET done` is the thank-you page ("Thank you. {name} has your details and will be in touch.") and clears the cookie. A stray GET on `consent|save|submit` is a 303 to `join`.
- **POST rules (as the portal):** `application/x-www-form-urlencoded` only (415), `Origin` must equal the site's origin (403), 4 KB body cap (413), the `JOIN_LIMIT` Workers rate-limit binding per `cf-connecting-ip` (120 per 60 s; skipped when the binding is absent, like `PORTAL_LIMIT`) answers 429 (the page's "Too many requests" message, or `{ok:false,error:"rate_limited"}` for the save).
- **Consent payloads** are built from `shared/generated/privacy-notices.json` like the portal's: `{notice_key:"customer_signup", version, hash[locale]}` for `signup_consent`; `{notice_key:"customer_signup_guardian", version, hash[locale]}` is sent as `guardian` to `signup_submit` **only when the guardian checkbox is ticked** (`guardian=1`), else `null`.
- **Autosave (`POST save`)**: the body holds the changed fields (only the known keys `name phone email dob address city nominee`; others are dropped by the Worker) and `active` (the focused field, or empty). It calls `signup_save` (no site lookup) and answers JSON `{ok:true}` or `{ok:false,error}` (the RPC's `consent_required`, `rate_limited`, `invalid_link`; 401 `invalid_link` without a cookie; 503 `unavailable` on failure), always `no-store`. The RPC drops or truncates bad values itself, so the live save never errors on content.
- **Submit (`POST submit`)**: sends all known fields plus `guardian`; `ok` -> **303** to `done` and the cookie is cleared; `invalid` (+ `field`) re-renders the form (400) with the typed values and the message for that field (`join.err_name|phone|email|dob|long|guardian`); `invalid_link` -> the invalid-link page; `consent_required` -> 303 to `join` (the consent step); `rate_limited` -> 429.
- **Under 18:** the form always contains the guardian block (`privacy.customer_signup_guardian.notice` and the checkbox `...consent`, **never `required` in markup**) and renders it hidden unless the saved or typed date of birth makes the person under 18 by India's date (`isMinor`, Asia/Kolkata) or the last submit came back with `field:"guardian"`. `join-client.js` shows or hides it as soon as the date of birth changes (and unticks it when hidden). The server decides whether the guardian consent is required.
- **Client (`join-client.js`, imports only `join-age.js`, under 6 KB):** on `input` it debounces 600 ms and POSTs the fields that differ from the last confirmed save, with the focused field as `active`; `focusin`/`focusout` send `active` (debounced); a **20 s heartbeat** while the page is visible (empty fields; retries unsaved ones); a polite live status line "Saving…" / "Saved" / "Not saved — check your connection" (strings are rendered into `data-*` by the server); a failed save is retried at the next change, focus or heartbeat. It never blocks or intercepts Submit.
- **Privacy page:** `privacyHtml` renders a `#signup` section (the `customer_signup` notice text) on every site's privacy page, like `#portal` (which still needs `portal === true`).
- **Build:** `scripts/build-web.sh` copies `join-client.js` and `join-age.js` (the Worker-only `join.js` is bundled by wrangler); `styles/` is copied whole. The privacy-page size cap in `test-web.mjs` is 102 KB (was 100) for the new routes.
- **Before the first deploy:** the `JOIN_LIMIT` ratelimit (`namespace_id` "1002") is unverified against the wrangler schema, like `PORTAL_LIMIT`; the backend migration for the sign-up RPCs must be applied and the gate (`PORTAL_RPC_KEY` and `private.portal_gate`) seeded, or every route answers 503 / "not available".

## Behaviour notes
- **Section order/visibility:** `content.sectionOrder` is followed (unknown keys dropped; `companies` is placed by `placeCompanies` when the order doesn't name it); `content.hidden` hides a section unless the schema marks it `pinned` (hero, contact), which is always shown (hero first, contact last if missing from the order). A section with no content renders nothing.
- **Escaping:** every agent string goes through `esc()`; links accept only `http(s)` (map, photo); phone/email are rebuilt from digits/validated before becoming `tel:`/`wa.me`/`mailto:`; JSON-LD escapes `<`. Multiline text uses `white-space: pre-line`, not `<br>`.
- **Images:** the hero photo is `loading` default (eager) with `fetchpriority=high`; it has explicit `width`/`height`. Every other image (bundled illustrations, uploaded offer images) is lazy with explicit size (see "Bundled images"). On the SSR page the measured LCP element is the `<h1>`.
- **Form:** posts `name, phone, email, interest (default "other"), message, honeypot` to `submit_enquiry` with the exact argument names from BACKEND.md. The client rules match the RPC (name 1-80, Indian mobile, email <= 120, message <= 500, interest from the catalog). The response is read by its exact `error` value: `{ok:true}` shows the thank-you; `rate_limited` shows the rate-limited message; `invalid` + `field` shows the inline error on that field (`site.form_error_phone`/`_email`/`_required`); `unavailable` or anything unexpected shows the generic error. HTTP 429 is also treated as rate-limited.
- **Footer:** `site.footer_advisor` + `site.footer_made_with`. No logos, ever: no insurer logo anywhere on a site; insurer names only in the companies section, as text (DECISIONS #77, #90).
- **Errors:** on the server a missing, unpublished or lapsed site is a 404 SSR unavailable page (`noindex`, no agent data, no scripts), and a backend error serves the static shell, whose `client.js` retries and shows the unavailable page (generic error text) if it fails again. Both set `noindex` and show no agent data.
- **Agency code:** shown when `about.showAgencyCode` is on and `profile.agency_code` is present (the RPC includes it only when that toggle is on).
- **Canonical:** `canonical_host` from the RPC (the active custom domain, or null) gives `https://<canonical_host>/` for `<link rel="canonical">` and `og:url`, also when the visitor is on the free link; on a custom host it is that host; otherwise the page's own URL (`/a/<slug>/`, with the slash).
